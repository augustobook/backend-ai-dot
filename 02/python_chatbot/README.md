# 🐍 Python Tutor: a LangChain + OpenAI chatbot

> 🇧🇷 Leia em português: [README.pt-BR.md](README.pt-BR.md)

A chatbot that answers **questions about Python programming** with didactic,
detailed answers: concept, commented code examples, common pitfalls and best practices.
It keeps the context of the conversation (follow-up questions work), answers in the
**same language as the question**, and politely declines topics unrelated to Python.

The same core logic powers three interfaces:

| Interface | Technology | Command |
|---|---|---|
| Interactive CLI | [rich](https://rich.readthedocs.io/) (Markdown, syntax highlighting, streaming) | `uv run python -m app.cli` |
| Web chat | [Chainlit](https://docs.chainlit.io/) (streaming, suggested questions) | `uv run chainlit run app/ui/chainlit_app.py -w --port 8001` |
| REST API | [FastAPI](https://fastapi.tiangolo.com/) (Swagger docs) | `uv run uvicorn app.api.main:app --reload` |

## Quick start

```bash
uv sync
cp .env.example .env      # fill in OPENAI_API_KEY (Windows: Copy-Item .env.example .env)
uv run chainlit run app/ui/chainlit_app.py -w --port 8001   # http://localhost:8001
```

Swap the last command for any interface in the table above. Details in
[Prerequisites](#prerequisites), [Configuration](#configuration) and [Running](#running);
Docker in [With Docker](#with-docker).

## Stack

- **Python 3.12** managed with **[uv](https://docs.astral.sh/uv/)**
- **LangChain** (`langchain-core`, `langchain-openai`): LCEL chain, prompt templates, message history
- **OpenAI** GPT-4 family chat model (default `gpt-4o-mini`, configurable)
- **LangSmith** (optional) for tracing and observability
- **FastAPI** + **Uvicorn**, **Chainlit**, **rich**, **pydantic-settings**
- **pytest** + **pytest-cov**, **ruff**, **mypy** (strict)

## Design decisions

- **Model and temperature.** The default is `gpt-4o-mini`: a GPT-4 family model with
  good quality for didactic answers at low cost and latency. Any GPT-4 family model
  can be used through `OPENAI_MODEL` (e.g. `gpt-4o`, `gpt-4.1`). The temperature is
  `0.3`: a tutor must be precise and consistent, with just enough variation to keep
  explanations natural. `max_tokens`, `timeout` and `max_retries` bound cost and latency.
- **Memory.** `RunnableWithMessageHistory` + `InMemoryChatMessageHistory`, one history per
  `session_id` (a CLI run, an API client or a browser tab), so conversations never mix.
  The store is in memory for simplicity; swapping it for Redis/SQL only changes
  `app/llm/history.py`.
- **History: never trimmed, sent only when needed.** A small, cheap model decides per
  question whether the conversation is needed; when it is, the **full** history is
  sent (no message is ever cut). See
  [How the conversation history is handled](#how-the-conversation-history-is-handled).
- **Limits measured in tokens.** Questions are limited to 5000 characters and each
  conversation to the model's context window, counted exactly with `tiktoken`; users
  are warned at 80%. See [Limits](#limits).
- **Prompt engineering** (`app/llm/prompts.py`, every decision is commented there):
  a concrete *role* (patient senior Python tutor); a fixed *answer format* (concept →
  commented code in Markdown → pitfalls → best practices, proportional to the
  question); a *language rule* (answer in the language of the latest message, code
  identifiers in English); a *scope rule*; use of the *conversation context*; and
  *honesty* (never invent APIs).
- **Scope restriction.** The system prompt allows only Python programming topics;
  anything else gets a short, polite refusal that suggests a related Python topic.
- **Testability.** `build_chat_chain(model, ...)` receives the model as a parameter
  (`BaseChatModel`), so tests inject a LangChain fake model and never call OpenAI.
- **Error handling.** OpenAI exceptions are translated into domain exceptions
  (`LLMAuthenticationError`, `LLMRateLimitError`, `LLMTimeoutError`,
  `LLMUnavailableError`), logged with technical details, and shown to users as friendly
  messages (CLI/web) or HTTP errors (API: 409, 422, 429, 503, 504).
- **Thin interfaces.** The CLI, the API and the Chainlit app only translate I/O and
  delegate to `ChatService`; no LLM logic is duplicated.

### Known trade-offs

- Since `langchain-core` 1.6, `RunnableWithMessageHistory` and
  `InMemoryChatMessageHistory` emit a `LangChainDeprecationWarning` recommending
  LangGraph persistence. They are still part of `langchain-core` and are used here
  because the project requirements ask for a pure LCEL chain with these classes.
  Only these two known warnings are silenced (`app/llm/__init__.py`), and
  `langchain-core` is pinned below 2.0, where they will be removed. The memory is
  isolated behind `SessionHistoryStore` and `build_chat_chain`, so a migration to
  LangGraph's checkpointer would not affect the service or the interfaces.
- Conversation memory lives in the process: it is lost on restart and is not shared
  between multiple API workers. A persistent store (e.g. Redis) would fix both.
  (The web interface reloads it from SQLite when a conversation is reopened.)

## How the conversation history is handled

Every conversation (`session_id`) keeps its **full history**: every question and
answer is saved and **no message is ever cut**. What changes from one question to
the next is only **whether that history is sent to the model**. Sending it to a
self-contained question would cost more and add noise; leaving it out of a follow-up
question would produce a wrong answer. A small **history router** decides, per question.

### Flow of one question

```
User question
      │
      ▼
0. Limits (ChatService._check_limits)
      ├─ question > 5000 characters?                       → refused (QuestionTooLongError)
      └─ system prompt + FULL history + question > budget? → refused (ConversationLimitError)
      │
      ▼
1. Is it the first question of the conversation?
      ├─ yes → there is no history: no extra call
      └─ no  ↓
2. ROUTER call (app/llm/router.py) ─ separate, small and cheap
      model : HISTORY_ROUTER_MODEL (default gpt-4.1-nano), temperature 0, ≤ 150 tokens
      input : router instructions + LAST 6 messages (each cut to 600 characters)
              + the new question
      output: structured  { "needs_history": true | false, "reason": "..." }
      │
      ▼
3. ANSWER call (the tutor: OPENAI_MODEL, default gpt-4o-mini, streamed)
      ├─ needs_history = true  → system prompt + FULL history + question
      └─ needs_history = false → system prompt + question (no history)
      │
      ▼
4. The question and the answer are SAVED in the history (in both cases)
```

### Example (one conversation)

| # | Question | Router decision | Sent to the tutor model |
|---|---|---|---|
| 1 | "Como criar uma lista em Python?" | none (first question) | the question only |
| 2 | "E como adiciono itens nela?" | `true`: "nela" refers to the list | full history (turn 1) + question |
| 3 | "O que são decorators?" | `false`: self-contained | the question only |
| 4 | "Me dá outro exemplo disso?" | `true`: "disso" refers to decorators | full history (turns 1-3) + question |

Question 4 works because turn 3 was saved even though question 3 was sent without
history.

### Rules

- **The router only decides; the answer gets everything.** The router sees a short,
  truncated excerpt (enough to detect references such as "it", "nela", "disso",
  "the code above"). When history is needed, the tutor model receives the **whole**
  conversation, never a summary or a cut.
- **When in doubt, send the history.** The router instructions end with
  "When in doubt, answer true", and any router failure (timeout, invalid output)
  also falls back to sending the history: extra context is harmless, missing
  context is not.
- **Cheap and fast on purpose.** The router uses a separate non-reasoning nano model
  with a tiny output budget. Reasoning models (e.g. the `gpt-5` nano family) can be
  cheaper per token but spend extra "thinking" tokens and time on a yes/no decision.
- **Why a router and not an agent.** A tool-calling agent ("call `get_history` when
  needed") would require two calls whenever history is needed and would complicate
  streaming. One structured decision call answers the same yes/no question.
- **Cost.** From the second question on, each question adds one small router call (a
  few hundred tokens on the cheapest model). In exchange, self-contained questions no
  longer carry the whole conversation to the tutor model.
- **Limits are independent of the decision.** The conversation budget always counts
  the full history, because it limits the size of the conversation itself.
- **Observability.** In LangSmith, each question shows a `history_router` run (with
  the `reason`) and the answer run carries metadata `history_used` and the tag
  `history:used` or `history:skipped`.
- **Configuration.** `HISTORY_ROUTER_MODEL` changes the router model;
  `HISTORY_ROUTER_ENABLED=false` disables the router (the full history is then always
  sent).

Where it lives: decision prompt and logic in [`app/llm/router.py`](app/llm/router.py)
(`ROUTER_SYSTEM_PROMPT`, `HistoryRouter`); the decision is applied in
`ChatService._prepare` / `_aprepare` ([`app/services/chat_service.py`](app/services/chat_service.py));
the chain drops the history when `use_history` is false
([`app/llm/chain.py`](app/llm/chain.py)).

### Limits

- **Question:** at most **5000 characters** (`MAX_QUESTION_LENGTH`), in every
  interface. Otherwise `QuestionTooLongError` (API: `422`).
- **Conversation:** the tokens of *system prompt + full history + new question* must
  fit in `OPENAI_CONTEXT_WINDOW - OPENAI_MAX_TOKENS` (128000 - 4096 = 123904 tokens by
  default), so the model always has room left for a full answer. Otherwise
  `ConversationLimitError` (API: `409`) and the user is asked to start a new
  conversation; the history is kept intact.
- **Answer:** at most `OPENAI_MAX_TOKENS` (default 4096 tokens).
- **Token counting** is **exact**, with the model's own tokenizer
  (`ChatOpenAI.get_num_tokens_from_messages`, which uses `tiktoken`). For reference:
  system prompt + a short question ≈ 430 tokens; a 5000-character question ≈ 630
  tokens. The counter is injected into `ChatService`, so tests use an approximate
  counter and stay offline.
- **Warning at 80%:** a toast in the web UI (not saved in the history), a yellow line
  in the CLI, and the `conversation_usage_percent` / `near_conversation_limit` fields
  in the API response.
- **Questions per client:** each IP may ask **10 questions per minute and 100 per
  day** (`RATE_LIMIT_PER_MINUTE`, `RATE_LIMIT_PER_DAY`; `0` disables) in the web UI and
  the API, since every question costs OpenAI tokens. Above that the web UI shows how
  long to wait and the API answers `429` with a `Retry-After` header; refused questions
  never reach OpenAI and are not counted. The CLI is local and never limited. Behind
  the reverse proxies (Caddy) the client is the rightmost public address in
  `X-Forwarded-For`, so a value forged by the client is ignored. Counters live in
  memory (one process; they reset on restart).

## Running

### CLI

```bash
uv run python -m app.cli
```

Commands: `/help` (list commands), `/clear` (clear the conversation history),
`/exit` or `Ctrl+C` (quit). Answers are streamed and rendered as Markdown with
syntax-highlighted code.

### Web interface

```bash
uv run chainlit run app/ui/chainlit_app.py -w --port 8001
```

Open <http://localhost:8001>. Chainlit uses port 8000 by default, the same as the
API; `--port 8001` lets both run at the same time. `-w` reloads on code changes.

### API

```bash
uv run uvicorn app.api.main:app --reload
```

Interactive docs (Swagger): <http://localhost:8000/docs>.

```bash
# Start a conversation (a session_id is generated and returned)
curl -X POST http://localhost:8000/chat \
  -H "Content-Type: application/json" \
  -d '{"message": "How do I create a list in Python?"}'

# Follow-up question in the same conversation
curl -X POST http://localhost:8000/chat \
  -H "Content-Type: application/json" \
  -d '{"session_id": "<session_id from the previous answer>", "message": "And how do I add an item to it?"}'

# Clear the conversation
curl -X DELETE http://localhost:8000/chat/<session_id>

# Health check
curl http://localhost:8000/health
```

| Method | Path | Description | Responses |
|---|---|---|---|
| `POST` | `/chat` | Ask a question (`{"session_id"?, "message"}`, message ≤ 5000 characters) | `200`, `409` (conversation full), `422` (invalid body), `429`, `503`, `504` |
| `DELETE` | `/chat/{session_id}` | Clear a conversation | `204` |
| `GET` | `/health` | Health check | `200` |

### With Docker

The [Dockerfile](Dockerfile) builds a multi-stage image with uv that runs the **web
interface** (Chainlit) as a non-root user on port 8000, with a health check. The
conversation history and the generated auth secret live in `/app/data`, so mount a volume
there to keep them across restarts:

```bash
docker build -t python-chatbot .
docker run --rm -p 8000:8000 --env-file .env -v chatbot-data:/app/data python-chatbot
```

Open <http://localhost:8000>. The `docker-compose.yml` at the repository root runs this same
image together with the other projects, behind a reverse proxy with HTTPS (see the
[root README](../../README.md)).

## Web interface

The Chainlit app (`app/ui/chainlit_app.py`) offers:

- **Suggested questions** on the welcome screen (create a list, list vs. tuple,
  decorators, exception handling), each with an icon.
- **Streaming**: the answer appears token by token, with Markdown and code highlighting.
- **New chat**: the "New Chat" button starts a fresh conversation; the previous
  history is released from memory.
- **Friendly errors**: an invalid key, rate limit or timeout is shown as a chat
  message in Portuguese.
- **Light and dark themes** (toggle in the UI; colors in `public/theme.json`).
- Optional display of the LangChain steps (`CHAINLIT_SHOW_CHAIN_STEPS=true`).

The interface is branded **"Chatbot de Python DOT Group"** and shown in **Brazilian
Portuguese** (the bot still answers in the language of each question):

- `.chainlit/config.toml`: assistant name, `language = "pt-BR"`, default theme.
- `.chainlit/translations/pt-BR.json`: Chainlit's own texts (input placeholder,
  menus, buttons), adapted from the bundled `pt-PT` translation.
- `chainlit.md`: welcome page ("Leia-me"), in Portuguese.
- `app/ui/helpers.py`: starter labels and error messages in Portuguese.
- `public/logo_dark.svg`, `public/logo_light.svg`: logo shown in place of Chainlit's.
- `public/avatars/chatbot_de_python_dot_group.svg`: assistant avatar.
- `public/custom.css`: hides the empty-state box of the conversation list.

### Conversation list (history)

The sidebar lists previous conversations, which are stored in **SQLite**
(`data/chat_history.db`, created automatically; path set by `CHAINLIT_DATABASE_PATH`).

- The chat is **open to everyone, with no login screen**. Chainlit only shows the list
  for a logged-in user, so a `header_auth_callback` logs every visitor in as the same
  shared user ("Visitante"). As a result, **all visitors see the same list**.
- `app/ui/persistence.py` adapts Chainlit's `SQLAlchemyDataLayer` to SQLite (creates
  the tables and serializes lists/dicts, which SQLite cannot store directly).
- Reopening a conversation (`on_chat_resume`) rebuilds the model's memory from the
  saved messages, so follow-up questions keep working.
- Chainlit signs the session cookie with `CHAINLIT_AUTH_SECRET`. If it is not set, a
  secret is generated once and saved in `data/.chainlit_auth_secret`.

Only the web interface persists conversations; the CLI and the API keep their
memory in process.

## LangSmith tracing

Tracing is optional and controlled only by environment variables:

```dotenv
LANGSMITH_TRACING=true
LANGSMITH_API_KEY=<your LangSmith key>
LANGSMITH_PROJECT=python-chatbot
```

Run any interface and open <https://smith.langchain.com> → *Projects* →
`python-chatbot`. Each run is named `python_tutor_chat` and carries:

- metadata `session_id` and `interface` (`cli`, `api`, `web` or `script`);
- tags `python-tutor` and `interface:<name>`.

Filter by these to follow a whole conversation or compare interfaces. Each trace shows
the full history, the rendered prompt, the model call (tokens, latency) and the
parsed answer. Without these variables the application works normally, with no tracing.
